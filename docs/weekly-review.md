# 개발 기록 요약과 검토 순서

## 현재 상태

Java/Spring 헥사고날 모듈, 순수 코어와 교체 가능한 포트, demo mock 질문 흐름, 현재 문서/권한/버전 필터, 엄격 JSON 입력과 합성 데이터 계약을 준비했다. 실제 검색·LLM·저장소·운영 인증·품질 eval은 미구현이다.

| 날짜 | 변경 | 검증 기록 |
|---|---|---|
| 2026-10-28 | 아키텍처·프로젝트 뼈대와 계약 | 전체 오프라인30건 통과 |
| 2026-10-29 | 기존 기반 재현과 모듈 검토 위치 정리 | 전체30건 재현. up-to-date로 fresh compile/clean 미실행 |
| 2026-10-30 | mock 질문의 소스·포트·테스트 추적표 | 관련22건 test phase 통과. 기능 추가 없음 |
| 2026-11-02 | 기존 합성6case 로더의 최소 계약 테스트1건 | 전체31건 통과. 품질 평가기는 아님 |

22건은 기존30건의 일부이며 누적52건이라는 뜻이 아니다. 이후 새 계약1건을 추가한 전체 합계가31건이다. 자세한 단계별 범위는 [검증 기록](verification.md)에 있다.

## 실행 방법

프로젝트 root에서 `mvnw.cmd -B verify` 또는 `sh ./mvnw -B verify`를 실행한다. 최초 공개 의존성 다운로드와 테스트 중 외부 서비스 호출을 구분한다. 이미 준비된 동일 캐시에서만 `-o`를 사용한다. 기본 비웹/선택적 demo 실행은 [실행 JAR 명령](verification.md#재현-명령--실행-jar)을 따른다.

## 리뷰 순서

1. [README](../README.md)의 현재 구현 상태와 모듈을 확인한다.
2. [아키텍처](architecture.md)에서 코어 의존성과 바깥 bootstrap 조립 방향을 읽는다.
3. [mock 질문 추적](mock-question-trace.md)의 예상 응답과 실제 소스·포트·테스트를 대조한다. 예상 JSON 전체가 실제 HTTP end-to-end로 검증됐다는 뜻은 아니다.
4. [합성 case 계약](eval-case-contract.md)에서 테스트 전용 reader와 데이터/label 관계를 확인한다.
5. [권한·문서 변경](security-and-lifecycle.md), [평가 계획](../eval/README.md), [백로그](backlog.md)의 미구현과 채택 조건을 검토한다.

## 남은 결정과 다음 작은 작업

- 실제 검색 전략/버전/프로토콜과 baseline 비교 조건
- 원본·metadata 저장소, 운영 principal/권한 원천, ACL revision·변경/삭제 중 일관성 정책
- chunk 정답·순위 grade·충실성 rubric과 실제 품질/비용 평가기
- 기본 검색·LLM·평가 계약 뒤의 온톨로지/KG 검토, 데이터·목표·효과가 확보될 때만 GNN 후속 실험

바로 다음 계획은 lexical baseline의 요청/응답 매핑 계약 한 조각이다. 로컬 fixture 범위부터 정하고 실제 클러스터·모델을 함께 연결하지 않는다. 별도 교육용 GNN 샘플은 이 프로젝트의 구현 완료가 아니다.
