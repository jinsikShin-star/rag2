# 화면 설계 안내와 전체 목록

[기획 안내](../README.md) · [MES 업무](../01-mes-workflows.md) · [데이터·권한](../02-data-contract-and-security.md) · [탄소 업무](../04-carbon-workflows.md)

> 기준일: 2026-11-04 · 화면 설계 버전: 0.2 · 상태: **문서 초안, 업무 사용자 검토 전**
> 실행 가능한 화면·인증·API가 아니다. 아래 배치·세부 이벤트·우선순위는 설계 제안이며 기존 제품 기획의 미결정 사항을 확정하지 않는다. 예시 식별자·수량·조직은 모두 가상이다.

## 1 이번에 볼 시나리오와 범위

생산 계획 담당자가 사용할 품목의 현재 승인 버전과 단위 근거를 확인한다. 품질 담당자는 그 품목으로 만들어진 LOT를 찾아 일부 보류 수량과 계보를 확인한다. 승인된 기준정보나 원천 실적을 목록에서 바로 덮어쓰는 대신, 권한 있는 새 개정·정정 요청으로 연결한다.

읽는 순서는 전체 목록 → 공통 이벤트 규칙 → [품목 목록·상세](S02-product-master.md) → [LOT 목록·상세](S05-lot-trace.md) → [검사·품질 보류 목록·상세](S06-quality-hold.md)다. 새 화면을 작성할 때는 [화면별 작성 표준](screen-spec-template.md)을 사용한다.

- 기존 기획의 상위 업무 화면은 **MES 14개 + 탄소 14개 = 28개**다. 이 숫자는 웹 페이지·모달·탭의 최종 개수가 아니다.
- 1차(2026-11-03) 상세화 대상은 S02 안의 `S02-L` 목록·`S02-D` 상세, S05 안의 `S05-L` 목록·`S05-D` 상세, **총 4개 뷰의 문서 초안**이다. S02의 BOM·라우팅·설비 등 모든 하위 화면을 설계한 것은 아니다.
- 2차(2026-11-04)는 S06 안의 `S06-L` 검사·보류 목록과 `S06-D` 검사 상세·처분 검토 **2개 뷰**의 초안을 추가했다. 누적 **6개 뷰**이며 원천 반영·물리적 보류 해제/재작업/폐기 실행폼은 후속이다.
- S02·S05·S06 외 상위 화면은 아래 목록만 정리했으며 상세 와이어프레임과 이벤트 설계는 미착수다. 이번 초안도 사용자 승인·실제 UI 구현·수용 테스트 통과를 뜻하지 않는다.
- `S01~S14`는 기존 MES 기획 ID를 유지한다. `C01~C14`는 기존 탄소 화면 순서에 붙인 **문서 참조용 ID 제안**이다. URL·API 식별자로 확정한 것이 아니다.

## 3 전문가용 공통 레이아웃 제안

데스크톱은 조밀한 표와 근거 패널을 함께 사용한다. 아래는 배치 설명용 와이어프레임이며 픽셀·색·UI 라이브러리는 미정이다.

```text
+----------------------------------------------------------------------------------+
| 서비스명 | 조직: 가상조직 / 사업장: 가상공장 [범위변경] | 사용자·역할 [세션]        |
| [샘플 데이터]  [경량 작성 / 기존 MES 읽기 연계]  원천: MES-A  최종확인: 시각·지연    |
+------------------+---------------------------------------------------------------+
| 업무 홈          | 기준정보 > 품목 > P-EXAMPLE / rev3                              |
| 기준정보         | 제목 + [초안/승인/대체됨] + 담당자 + 다음 행동                  |
| 생산             | 범위·기간·상태 필터 [조회] [초기화]                              |
| 로트·품질        +------------------------------------------+--------------------+
| 에너지·데이터    | 목록 / 탭 / 입력폼                       | 선택 대상 요약     |
| 검토·마감        | 필드명·단위·출처·버전                    | 오류·차단 사유     |
| 탄소 기준·입력   | 행 선택 / 페이지 / 정렬                  | 근거·이력 링크     |
| 계산·분석        |                                          | 영향 범위·한계     |
| 승인·공유        +------------------------------------------+--------------------+
| 관리             | 검증 요약 / 마지막 서버 저장 시각 / [취소] [권한 있는 주행동]   |
+------------------+---------------------------------------------------------------+
```

- 조직·사업장·허용 제품 범위, 샘플 여부, 데이터 원천, 작성/읽기 모드, 조회 기준 시각을 화면 위에 유지한다. 단일 배지로 품질·생산 흐름·계산·공유 상태를 섞지 않는다.
- 범위를 바꾸면 진행 중 조회를 무효화하고 선택 행·임시 입력을 정리한다. 늦게 도착한 이전 범위 응답을 새 화면에 표시하지 않는다. 저장 중에는 결과를 확인한 뒤 이동하도록 안내한다.
- 목록에서 상세로 이동해도 허용된 필터·정렬·페이지 맥락을 복원한다. 직접 링크 진입도 서버 권한을 다시 검사한다. 권한 없는 대상의 존재·수량·이름을 오류 메시지로 누출하지 않는다.
- 각 목록은 조회된 범위·건수 기준·페이지 범위를 표시한다. 전체 합계와 현재 페이지 합계를 구별하고, 권한 밖 데이터가 포함된 전사 합계를 노출하지 않는다.
- 복잡한 경계·배분·승인 검토는 데스크톱 우선이다. 작은 화면은 요약 카드→한 탭씩 상세→근거 확인으로 축소한다. 열을 단순히 숨겨 단위·상태·출처가 사라지게 하지 않는다. 현장 입력 전용 화면은 S04에서 별도로 설계한다.

## 4 모든 버튼에 적용할 이벤트 계약

다음은 UI·서버가 앞으로 맞춰야 할 **동작 제안**이다. 현재 프로젝트의 실제 API 응답이나 구현 보장을 뜻하지 않는다. 화면별 이벤트 표는 이 공통 규칙과 그 화면의 차이를 함께 명시한다.

| 순서 | 공통 처리 | 화면에 보일 결과 / 중단선 |
|---|---|---|
| 1 입력 | 대상 ID·현재 revision·선택 범위·사용자 입력을 고정한다. 쓰기 요청은 한 사용자 의도에 작업 식별자를 둔다. | 선택 대상·변경 내용·단위·필수 사유를 확인하고 요청 중 해당 버튼을 잠근다. |
| 2 검증 | 형식·필수·단위·유효일·버전·상태·수량수지를 검사한다. 브라우저 검사는 빠른 피드백이며 서버 검사를 대체하지 않는다. | 필드 옆 오류 + 상단 오류 요약. 첫 오류로 포커스를 옮기고 입력을 보존한다. |
| 3 권한 | 서버가 tenant/site/product/artifact/action 범위와 현재 역할·원천 소유권을 다시 검사한다. | UI 숨김/비활성화만으로 허용하지 않는다. 권한 회수면 저장하지 않고 재인증·권한 확인 경로를 안내한다. |
| 4 상태 변화 | 현재 revision과 기대 상태가 맞을 때만 한 번 반영한다. 승인본/원천 사건은 새 개정·정정으로 연결한다. | 응답 전 `저장 완료` 금지. 승인·마감·외부 공유를 한 버튼으로 연쇄 확정하지 않는다. |
| 5 성공 | 서버의 대상 ID·새 revision·확정 시각·상태를 받아 상세/목록을 갱신한다. | 성공 메시지, 변경 결과와 다음 행동. 저장 시각은 클라이언트 클릭 시각과 구분한다. |
| 6 실패 | 입력 오류, 권한, 상태/버전 충돌, 원천 지연, 서비스 실패를 구분한다. | 사용자가 고칠 부분과 확인할 담당자·추적 ID를 표시한다. 내부 스택·비밀값·타 고객 식별자는 노출하지 않는다. |
| 7 중복·불명 | 같은 작업 식별자+같은 입력은 기존 처리 결과를 확인한다. 다른 입력으로 재사용하면 충돌로 거절한다. | 시간초과는 실패 확정이 아니다. `처리 결과 확인 중/확인 필요`로 두고 작업 상태를 조회한다. 새 키로 맹목 재전송하지 않는다. |
| 8 감사·후속 | 쓰기·승인·반려·다운로드 등 정책 대상 동작의 행위자·범위·전후 revision·사유·결과·상관 ID를 남긴다. | 감사 권한에 맞는 이력 링크. 원문 기밀·토큰·불필요 개인정보를 로그에 복사하지 않는다. 영향 검토/알림은 별도 상태로 표시한다. |

### 충돌과 재시도의 공통 상태

- **다른 사용자가 먼저 변경:** 덮어쓰기 금지. 서버 최신본과 내 변경을 비교하고, 다시 검토한 뒤 새 의도로 제출한다. 충돌 표시는 오류 코드/상태 계약을 정할 때 API에 매핑한다.
- **응답 유실·시간초과:** 작업 ID로 처리 여부를 확인한다. 성공이면 동일 결과를 연다. 진행 중이면 기다림/재조회를 제공한다. 확인할 수 없으면 `결과 불명`을 유지하고 지원·대사 경로를 안내한다. 확인 없이 새 작업으로 복제하지 않는다.
- **조회 재시도:** 읽기 재시도는 원래 범위와 필터로 수행한다. 이전 성공 데이터는 오래됨 배지와 기준 시각을 붙이거나, 범위가 달라졌으면 비운다. 부분 로드 실패를 빈 데이터/0건으로 표시하지 않는다.
- **새로 고침·뒤로 가기:** 미저장 변경이 있으면 이탈 확인을 제공한다. 초안 자동 저장은 현재 설계의 기본 보장이 아니다. 제안 기본은 명시적인 `초안 저장`이며 서버 확인 후에만 저장으로 표시한다. 민감한 입력을 브라우저 영구 저장소에 임의 보관하지 않는다.
- **원천 연계 모드:** 원천 소유 데이터는 읽기와 정정 요청으로 제한한다. 경량 작성 모드도 해당 역할·상태·개정 검사를 통과해야 한다. 모드 전환으로 기존 데이터를 소리 없이 복제·변경하지 않는다.
- 작업 식별자 수명·보존, 상태 조회 방법, 잠금/취소·재인증 후 초안 복구, 논리 오류의 API 상태 매핑은 **구현 전 미결정**이다.

## 5 빈 상태·접근성·조회 품질

| 상태 | 공통 표시와 행동 |
|---|---|
| 최초 로딩 | 헤더·현재 범위 유지, 표/패널 로딩 표시. 아직 수량·권한 판정이 끝나지 않은 동작을 활성화하지 않는다. |
| 데이터 없음 | `등록된 데이터 없음`과 `필터 결과 없음`을 분리한다. 허용된 새 초안/수집 안내 또는 필터 초기화를 제시한다. |
| 접근 불가 | 일반적인 접근 불가 안내와 담당자 확인 경로. 대상의 기밀 속성·다른 tenant 존재를 공개하지 않는다. |
| 조회 실패 | 실패한 패널과 재시도 범위를 표시한다. 목록 성공·계보 실패라면 전체가 정상이라고 표시하지 않는다. |
| 지연·오래됨 | 원천 기준 시각·동기화 시각·지연 범위를 구분한다. 불완전한 계보/미수신 구간을 `없음`으로 단정하지 않는다. |
| 검증 실패 | 오류 요약에서 필드로 이동, 단위와 허용 조건을 함께 안내한다. 색만으로 차단/경고를 구분하지 않는다. |
| 저장 중·결과 불명 | 진행/확인 필요 배지, 중복 제출 차단, 상태 확인 동작. 조회 실패와 쓰기 실패를 혼동하지 않는다. |

키보드로 메뉴·필터·행·버튼·대화상자를 순서대로 사용할 수 있어야 한다. 표에는 제목/열 헤더/정렬 상태/행 선택 설명을 두고 수량 옆 단위를 유지한다. 모달 진입 시 제목 또는 첫 필드로, 닫을 때 호출 버튼으로 포커스를 돌린다. 오류·로딩 완료·저장 결과는 보조기술이 인지할 수 있게 설계한다. 화면 낭독·키보드·대비의 실제 검증은 UI 구현 단계의 수용 기준이며 현재 통과한 테스트가 아니다.

이는 날짜를 확정한 개발 일정이 아니다. 평일 점심 작업에서는 최신 일지·피드백을 읽고 한 묶음을 다시 작은 한 가지 검토 결과로 나눈다. 11/03 오후 직접 요청은 정오 작업과 별도로 기록했고, 11/04 S06은 기존 점심 작업 창의 한 문서 묶음으로 진행한다. 반복 작업의 실행·알림은 기존 일정 흐름이 관리하며 이 문서가 새 스케줄러를 만들지 않는다.

1. 화면 ID와 이벤트 ID는 변경 이력에서 추적한다. 기존 ID를 다른 의미로 재사용하지 않는다.
2. UI 개발 시 문서→컴포넌트/라우트→실제 API 계약→수용 테스트를 화면별 매핑 표에 연결한다. 현재는 전부 미매핑이며 화면 문서가 실제 API 계약을 만들어 낸 것으로 표시하지 않는다.
3. 구현하면서 버튼·필드·상태가 바뀌면 같은 변경 묶음에서 해당 문서와 수용 기준을 갱신한다. 소스와 다른 스크린샷만 남겨 기준으로 쓰지 않는다.
4. 문서 상태는 `초안 → 업무 검토 → 합의 → 구현 매핑 → 구현/검증`으로 제안한다. 체크는 근거 링크와 검토자/날짜가 있을 때만 한다. 지금은 첫 상태다.
5. 중요한 변경은 전/후 동작·이유·영향 화면·미결정·실제 검사 결과를 개발일지에 적는다. 금요일에는 이번 주 실제 변경과 다음 결정 한 가지를 요약한다.

## 7 누적 묶음의 검토 기준과 미결정

- [ ] 사용자 시나리오에서 품목 승인본과 실제 LOT 원천을 구별할 수 있다.
- [ ] 1차 네 뷰와 S06 추가 두 뷰의 모든 버튼이 입력·검증·권한·상태·성공·실패·중복·감사 후속 동작으로 추적된다.
- [ ] 일부 보류·분할·병합·포장집합, 단위·원천·개정·조회 한계의 표기가 서로 충돌하지 않는다.
- [ ] 조회/읽기 연계만으로 원천 사실을 수정하거나 MES 승인으로 탄소 발행을 허용하지 않는다.
- [ ] 업무 사용자와 빈/지연/충돌/결과 불명 상태 및 키보드 흐름을 검토한다.
- [ ] 기존 승인본·과거 작업지시·원천 사건이 새 초안 저장으로 바뀌지 않는지 확인한다.
- [ ] S06에서 표본 검사 결과·보류/처분 요청·검토 승인·원천 반영/물리 실행 상태를 구별하고, 요청/승인만으로 가용수량을 확정하지 않는지 검토한다.

첫 산업·공정·고객 사용 목적, 실제 표본, 기준정보 승인 역할, 부분 보류 표현 방식, 원천별 정정 책임, 작업 식별자/조회 계약, 데이터 보존·사용권·운영 조건은 아직 미결정이다. [개발 착수 승인 TODO](../06-ai-discovery-and-decisions.md#8-개발-착수-승인-todo)를 해소하고 범위를 승인하기 전에는 이 문서를 UI 개발 착수 승인으로 사용하지 않는다. GNN은 기존 후속 실험 TODO이며 이번 화면 묶음에서 학습·추론·그래프 실행을 설계 완료하거나 구현하지 않았다.
